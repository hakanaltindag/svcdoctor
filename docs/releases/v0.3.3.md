# svcdoctor v0.3.3

The last public release was **v0.1.0**, which diagnosed PostgreSQL only and shipped as source
and binaries. These notes cover everything user-visible since then.

`v0.2.0`, `v0.3.0`, `v0.3.1` and `v0.3.2` are Git tags, not published releases. Each is retired
rather than reused, because a semver tag is never moved (ADR 0062 §13, §21c) and the Go checksum
database records a tag permanently once it is fetched.

- `v0.2.0` marked a development milestone and was never published.
- `v0.3.0` was tagged on a commit that contained no `Dockerfile` and no release workflow, so the
  tag push triggered nothing at all.
- `v0.3.1` reached the release pipeline and was stopped by it. The PostgreSQL integration suite
  failed on the Linux runner: the fixture bind-mounted a TLS private key with the runner's
  ownership, and PostgreSQL will not start on a key it does not own. `job.needs` held — the OCI
  and publication jobs were **skipped**, so nothing was published.
- `v0.3.2` published its container image successfully, and no GitHub Release. The job that
  creates one was added after that tag was cut, and a tag runs the workflow from its own tree —
  so the machinery could not reach it. The image is real and remains addressable by digest.

**v0.3.3 is the first release to complete the whole path**: signed multi-arch image, SBOM,
provenance, GitHub Release, and Latest. Everything below is new to anyone upgrading from v0.1.0.



## Highlights

- **Apache Kafka diagnosis.** `svcdoctor diagnose kafka` is a complete BASIC journey: DNS, TCP,
  TLS, `ApiVersions`, SASL mechanism discovery, `PLAIN` and `SCRAM-SHA-256` authentication, and
  `Metadata` — plus credential-free verification of every advertised broker.
- **A published container image.** `ghcr.io/hakanaltindag/svcdoctor:v0.3.3`, `linux/amd64` and
  `linux/arm64`, distroless, no shell, non-root, read-only-root-filesystem capable.
- **A verifiable supply chain.** Reproducible platform images, a CycloneDX SBOM, build
  provenance and a keyless cosign signature over the image digest.
- **IPv4 and IPv6 literal targets** are first-class for both services.
- **TLS trust and peer identity are separated**, and disabled verification is disclosed in the
  report rather than being a silent flag.

## Kafka diagnosis

`svcdoctor diagnose kafka --host … --port …` reaches `Kafka metadata obtained`.

- **Mechanism discovery before authentication.** svcdoctor asks the broker which SASL
  mechanisms it offers and refuses to guess. An unsupported mechanism produces `UNKNOWN` and a
  capability failure class — never a claim that the broker rejected your credential.
- **One credential-bearing attempt, ever.** Authentication happens exactly once, on the
  bootstrap endpoint you named. Advertised brokers get DNS, TCP and TLS and nothing else: no
  credential is read, revealed or sent to a host that discovery found rather than you.
- **Advertised-listener reachability.** The common Kafka failure — a bootstrap endpoint that
  answers perfectly while the brokers it advertises are unreachable from where you are —
  reports both halves, with the vantage point recorded.
- **`PLAIN` and `SCRAM-SHA-256`.** `SCRAM-SHA-512` and `AWS_MSK_IAM` are **not** implemented
  and are declined explicitly.

## PostgreSQL

The v0.1.0 journey is unchanged in shape and gained the improvements below through shared
transport work: literal targets, the TLS trust/identity split, and the stricter flag validation
described under *Tightened CLI behaviour*.

## Authentication and TLS

- **Trust and identity are different questions.** Trust answers *whose certificate is this*;
  identity answers *is this the peer I meant*. DNS resolution is never identity authority.
- **Disabled verification is disclosed.** When a run disables TLS verification, the terminal
  output says so in the header and on each handshake row — read from two independent fields, so
  a renderer cannot infer one from the other.
- **A credential crosses only a verified TLS channel.** A policy refusal is `SKIPPED` with
  `EXEC_SKIPPED_BY_POLICY` and **zero bytes sent**.

## IP literal targets

`--host 10.0.0.5` and `--host 2001:db8::1` are first-class for both services. An address is not
a name, so a run given one **resolves nothing and records nothing about resolution** — the
report contains no `dns.lookup` node at all, which makes a DNS finding structurally unreachable
rather than suppressed. One address has one spelling; IPv4-mapped forms are unmapped, and a
zone identifier is refused rather than silently accepted.

## Container and Kubernetes

- `ghcr.io/hakanaltindag/svcdoctor:v0.3.3` — `linux/amd64` and `linux/arm64`.
- `gcr.io/distroless/static-debian12:nonroot` plus one static binary. **No shell, no package
  manager.** Runs as UID **65532**, with a read-only root filesystem and all capabilities
  dropped.
- Secrets are read from files or stdin, never from the environment.
- Hardened Kubernetes `Job` examples in `examples/kubernetes/`. svcdoctor never calls the
  Kubernetes API and needs no ServiceAccount token, Role or RoleBinding.

Running in a container is not just packaging: a container is a **network position**, and every
connectivity finding is qualified by where it was measured from.

## Supply chain

Every release carries three distinct artifacts answering three different questions:

| Artifact | Question |
|---|---|
| CycloneDX SBOM | what components are inside |
| Build provenance | how and from what it was built |
| cosign signature | is this from us, unmodified |

- **Reproducible platform images.** The same commit built with `scripts/build-image.sh` yields
  identical `linux/amd64` and `linux/arm64` manifest digests. The multi-arch *index* digest does
  not reproduce, because it references attestations that legitimately contain build-time data —
  claiming otherwise would mean giving up provenance.
- **One SBOM format.** CycloneDX JSON, attached to the image index with
  `cosign attest --type cyclonedx`. BuildKit's SPDX SBOM is deliberately disabled: two
  independently produced inventories can disagree, and there would be no rule for choosing.
- **Keyless signing** over the image **digest**, never a tag, using GitHub Actions OIDC. There
  is no long-lived signing key.
- Verification is a release gate, constrained to this repository's workflow at this tag.

## Compatibility evidence

Levels are graded and enforced by test — a row cannot claim a tested level for a platform
nobody ran against.

| Platform | Level |
|---|---|
| Apache Kafka 4.0.0 | **3 — supported BASIC**, committed 3-broker KRaft fixture |
| PostgreSQL 18 | **3 — supported BASIC**, committed fixture |
| Redpanda **self-hosted** v25.1.9 | **3 — supported BASIC**, committed fixture; `PLAIN` and `SCRAM-SHA-256` |
| OCI `linux/amd64`, `linux/arm64` | **3 — supported**, both run natively |
| Kubernetes Job (k3s v1.33.3) | **2 — run**, no committed fixture |

**Not validated, and not claimed:** Redpanda Cloud, Confluent Cloud and every other managed
provider are documentation-only. Self-hosted Redpanda evidence does **not** transfer to Redpanda
Cloud. AWS MSK SASL/SCRAM is `SCRAM-SHA-512` only and MSK IAM needs `AWS_MSK_IAM`; neither is
implemented. No cloud credential was used at any point.

## Tightened CLI behaviour

**PostgreSQL now refuses TLS options that `--tls disable` makes inert.** Three previously
accepted invocations now exit **2**:

```
--tls disable --tls-ca-file ca.pem
--tls disable --tls-server-name x
--tls disable --tls-insecure
```

They were silently ignored before, so nothing that worked stops working — but a script that
passed them was describing an intent svcdoctor was not honouring. Kafka always rejected them.

## Known limitations

- Kafka `SCRAM-SHA-512` and `AWS_MSK_IAM` are not implemented.
- A PostgreSQL password must be printable ASCII (`U+0020`–`U+007E`). PostgreSQL applies
  SASLprep; svcdoctor implements only the range over which SASLprep provably changes nothing.
  MD5, cleartext and `SCRAM-SHA-256-PLUS` are observed and declined — always as `UNKNOWN` plus a
  capability failure class, never as a claim that the peer rejected the credential.
- `SummaryStatus == OK` means *no ERROR or CRITICAL target-side problem was proven*. It does
  **not** mean a session was established or that the target is healthy.
- No cluster health, producer/consumer health, topic/partition/ISR state, consumer lag,
  performance benchmarking or automatic remediation. Stage duration is measured, not judged.
- NetworkPolicy enforcement is **unverified** — the test cluster accepted NetworkPolicy objects
  without enforcing them. svcdoctor depends on no NetworkPolicy API.

## Install

Container:

```sh
docker pull ghcr.io/hakanaltindag/svcdoctor:v0.3.3
```

Production should pin the digest — a tag is a name resolved at pull time, a digest is the
artifact:

```sh
docker buildx imagetools inspect ghcr.io/hakanaltindag/svcdoctor:v0.3.3 \
  --format '{{json .Manifest.Digest}}'
```

Go:

```sh
go install github.com/hakanaltindag/svcdoctor/cmd/svcdoctor@v0.3.3
```

## Verification

```sh
cosign verify \
  --certificate-identity-regexp '^https://github\.com/hakanaltindag/svcdoctor/\.github/workflows/oci-stage-verify\.yml@refs/tags/v0\.3\.1$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/hakanaltindag/svcdoctor@sha256:<release digest>

cosign verify-attestation --type cyclonedx \
  --certificate-identity-regexp '^https://github\.com/hakanaltindag/svcdoctor/\.github/workflows/oci-stage-verify\.yml@refs/tags/v0\.3\.1$' \
  --certificate-oidc-issuer https://token.actions.githubusercontent.com \
  ghcr.io/hakanaltindag/svcdoctor@sha256:<release digest>
```

## Upgrade notes

The report **schema version is still 1**. Nothing in this release changes the machine-readable
contract: no finding code, failure class, state, step or dependency was added or removed, and
the JSON shape is unchanged. Terminal presentation changed — disabled TLS verification is now
disclosed — but the terminal is a derived view and JSON is canonical.

The only behavioural tightening is the three PostgreSQL invocations above, which now exit 2.
